## 一、引言：当模型不再只是一个"聊天机器"

2023 年 ChatGPT 横空出世后，人们很快发现了一件事：再聪明的大模型，也有"与世隔绝"的尴尬——

- 你问它"今天天气怎么样？"，它不知道，因为训练数据截止到几个月前。
- 你想让它帮你订一张机票，它做不到，因为它无法访问外部系统。
- 你让它做一道数学题 `12345 × 67890`，它可能算错，因为它在"猜"结果而不是真正计算。

面对这些局限，两条路线浮现出来：

1. **工具调用（Function Calling）**：给模型装上"手"，让它能调用外部 API、执行代码、查询数据库。
2. **规模扩展（Scaling Laws）**：把模型做得更大，看看会涌现出什么新能力。

这两条路线不是对立的，而是互补的——工具调用解决了"能力边界"的问题，Scaling Laws 揭示了"规模与性能"的量化关系。本文对两者进行深度解析。

## 二、大模型工具调用：给 AI 装上"手"

### 2.1 什么是 Function Calling

**Function Calling**（函数调用，也称 Tool Use）是指：大模型在生成回复时，不直接输出文本，而是输出一个**结构化的函数调用请求**，由外部程序执行后，将结果返回给模型继续生成。

用一个简单的例子来说明：

```
用户："查询 2026 年 6 月 17 日北京的天气"

模型内部决策：我没有实时天气数据，需要调用 get_weather 函数
    ↓
模型输出（不是回答给用户，而是给系统）：
{
  "function": "get_weather",
  "arguments": {
    "city": "北京",
    "date": "2026-06-17"
  }
}

系统执行 get_weather("北京", "2026-06-17") → 返回 "晴，25°C"
    ↓
模型收到结果，生成最终回复：
"2026 年 6 月 17 日北京天气晴，气温 25°C，适合出行。"
```

**核心洞察**：模型不再"编造"答案，而是学会了"我不确定就去查"。

### 2.2 工作机制：从声明到执行

完整的 Function Calling 流程包含五个步骤：

```
┌─────────────────────────────────────────────┐
│  1. 定义工具（Tool Definition）               │
│     声明函数名、描述、参数 Schema               │
├─────────────────────────────────────────────┤
│  2. 发送请求                                 │
│     Prompt + 工具列表 → 大模型 API             │
├─────────────────────────────────────────────┤
│  3. 模型决策                                 │
│     判断是否需要调用工具？调用哪个？传什么参数？    │
├─────────────────────────────────────────────┤
│  4. 执行函数                                 │
│     由客户端（而非模型）实际执行，获取结果         │
├─────────────────────────────────────────────┤
│  5. 结果返回                                 │
│     执行结果作为新消息追加，模型生成最终文本回复    │
└─────────────────────────────────────────────┘
```

**关键点**：模型**不执行**函数——它只输出调用请求。真正的执行在用户侧进行。这种设计有两个好处：
- 安全隔离：模型无法直接操作系统、网络、文件
- 灵活扩展：可以接入任意 API，不受模型限制

### 2.3 工具定义：怎么写一个函数声明

以 OpenAI 的格式为例，定义一个天气查询工具：

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "获取指定城市在指定日期的天气信息",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "城市名称，如'北京'、'上海'"
        },
        "date": {
          "type": "string",
          "description": "日期，格式为 YYYY-MM-DD"
        }
      },
      "required": ["city", "date"]
    }
  }
}
```

**设计工具定义的三个原则：**

1. **描述要精确**：`description` 是模型判断"什么时候该用这个函数"的唯一依据。模糊的描述会导致模型该调用时不调用，不该调用时乱调用。
2. **参数要完整**：所有必需参数都需声明 `required`，每个参数的类型和含义要清晰。
3. **命名要自解释**：函数名本身就是语义信号——`get_weather` 比 `func1` 好一万倍。

### 2.4 多工具调用：模型如何"选工具"

实际应用中，一个 Agent 通常拥有多个工具。模型需要根据用户意图，自主选择调用哪个（或哪些）工具：

```json
// 工具列表
[
  { "name": "search_web",      "description": "搜索互联网信息" },
  { "name": "get_weather",     "description": "查询天气" },
  { "name": "send_email",      "description": "发送邮件" },
  { "name": "calculate",       "description": "执行数学计算" },
  { "name": "query_database",  "description": "查询内部数据库" }
]

// 用户："帮我查一下北京的天气，如果明天有雨就发邮件提醒我"
// 模型决策：先调 get_weather，根据结果决定是否调 send_email
```

模型需要具备**工具编排（Tool Orchestration）** 能力——理解工具之间的依赖关系，按正确的顺序调用。现代模型（如 GPT-4、Claude 4 等）可以并行调用独立工具，串行调用有依赖的工具。

### 2.5 工具调用的典型应用场景

| 场景 | 工具类型 | 示例 |
|------|----------|------|
| **实时信息检索** | Web Search API | 查新闻、股价、体育比分 |
| **数据查询** | SQL / 向量数据库 | 企业内部知识库问答 |
| **外部操作** | REST API / RPC | 订票、下单、发送消息 |
| **精确计算** | 代码执行器 | 复杂数学、数据分析 |
| **文件操作** | 文件系统 API | 读写文档、生成报告 |
| **多模态处理** | 图像/音频 API | OCR 识别、语音合成 |

工具调用实质上把大模型从"封闭的知识库"变成了"开放的操作系统"——模型是调度中心，各种工具是外围设备。

## 三、Scaling Laws：规模带来的质变

### 3.1 什么是 Scaling Laws

**Scaling Laws（规模定律）** 描述的是：语言模型的性能如何随着**模型参数量（N）**、**训练数据量（D）** 和**计算量（C）** 的变化而变化。

2020 年，OpenAI 的 Kaplan 等人发表了开创性论文 *"Scaling Laws for Neural Language Models"*，发现了几个核心规律。

### 3.2 Kaplan 定律：三大核心发现

**发现一：性能与规模呈幂律关系**

模型在测试集上的交叉熵损失 $L$ 与三个变量之间遵循**幂律关系**：

$$
L(N) = \left(\frac{N_c}{N}\right)^{\alpha_N}
$$

$$
L(D) = \left(\frac{D_c}{D}\right)^{\alpha_D}
$$

$$
L(C) = \left(\frac{C_c}{C}\right)^{\alpha_C}
$$

其中 $\alpha_N \approx 0.076$、$\alpha_D \approx 0.095$、$\alpha_C \approx 0.050$。

**这意味着什么？** 要把损失降低一半，你需要将参数量扩大约 $2^{1/0.076} \approx 9100$ 倍——或者将数据量扩大约 $2^{1/0.095} \approx 1500$ 倍。收益递减非常明显。

**发现二：大模型更"样本高效"**

更大的模型不仅最终性能更好，而且**学得更快**——达到同样性能所需的训练步数更少。换句话说，大模型对每个训练样本的利用率更高。

```
性能
 ↑
 |     大模型 ────────────────
 |     ／               
 |    ／                
 |   ／   中模型 ────────
 |  ／    ／            
 | ／    ／             
 |／    ／   小模型 ────
 |    ／     ／
 |   ／     ／
 +──────────────────────→ 训练计算量
```

**发现三：最优批大小随模型规模增长**

更大的模型需要更大的批大小（batch size）来充分利用计算资源。这实际上影响了训练策略：不能简单地用训练小模型的超参数来训练大模型。

### 3.3 Chinchilla 定律：数据也很重要

2022 年，DeepMind 的 Hoffmann 等人提出了 **Chinchilla 缩放定律**，修正了 Kaplan 的一个关键结论。

Kaplan 认为模型规模比数据规模更重要，但 Chinchilla 发现：

> **在给定计算预算下，模型参数量和训练 token 数应该同比缩放——而不是一味堆参数。**

具体来说，对于给定的计算预算 $C$（FLOPs），最优配置是：

$$
N_{opt} \propto C^{0.5}, \quad D_{opt} \propto C^{0.5}
$$

也就是说，如果你把算力提高 4 倍，最优策略是把参数量翻倍**同时**把训练数据翻倍——而不是把参数量提高 4 倍。

这个发现直接影响了 Llama 系列等开源模型的训练策略：**用小一点的模型 + 更多数据，比大模型 + 少数据效果更好**。

### 3.4 涌现能力：量变引起质变

**涌现（Emergence）** 是 Scaling Laws 最引人入胜的现象：某些能力在模型规模超过某个阈值后突然出现，而在较小的模型中完全不存在。

涌现能力的典型例子：

![大模型涌现能力示意图](/images/blog/emergence-curves.png)

**关键特征：**
- 在临界点之前，模型完全不具备该能力（不是"做得不好"，而是"做不到"）
- 超过临界点后，能力迅速提升
- 不同能力有不同的涌现阈值

这解释了为什么 GPT-2（1.5B）没有展现出的推理能力，在 GPT-3（175B）中突然出现了——不是"改进"了，而是"涌现"了。

### 3.5 Scaling Laws 的实践指导

对普通开发者来说，Scaling Laws 的启示在于：

1. **不要在小模型上反复微调企图实现大模型的能力**：如果某个能力需要 70B 参数才能涌现，在 7B 模型上用再多的数据微调也只是"刻舟求剑"。

2. **数据质量与数据量同样重要**：Chinchilla 定律说的是"token 数"，但实际工程中，高质量的数据远比低质量的海量数据有效。

3. **推理阶段的 Scaling（如 CoT、Self-Consistency）也是 Scaling**：不仅训练阶段有 Scaling Laws，推理阶段增加计算（如让模型多思考几步）也能线性提升性能。

4. **RAG 是绕过 Scaling Laws 的实用策略**：与其训练一个能记住所有知识的大模型（昂贵），不如用检索增强（便宜且灵活）。

## 四、工具调用与 Scaling 的交叉点

工具调用和 Scaling Laws 不是两个孤立的话题，它们在实际系统中**互相补充**：

| 维度 | Scaling 路线 | 工具调用路线 |
|------|------------|------------|
| **解决问题** | 内部能力不足 | 外部能力缺失 |
| **成本** | 训练成本极高 | 推理成本适中 |
| **时效性** | 训练后固定 | 实时查询 |
| **可控性** | 黑盒涌现 | 白盒可控 |

一个值得注意的趋势是：**随着模型规模增大，工具调用的能力也在涌现**。小型模型即使给了工具定义，也不知道何时该调用、如何正确填写参数。而大模型（如 GPT-4、Claude 4 等）展现了近乎"本能"的工具使用能力——它们能理解工具的语义、判断调用的时机、甚至在工具执行失败后自行纠错。

这暗示了一个未来方向：**大型基础模型 + 丰富的工具生态**，模型本身不再需要"知道一切"，而是成为一个智能的**调度中心**。

## 五、总结

本文从两个角度解析了大模型的核心机制：

**工具调用（Function Calling）**：
- 模型通过生成结构化的函数调用请求，让外部程序执行实际操作
- 核心流程：工具定义 → 模型决策 → 客户端执行 → 结果返回 → 模型综合回复
- 解决了实时性、精确性、外部交互三大痛点
- 工具定义的质量直接影响调用正确率

**Scaling Laws（规模定律）**：
- 性能与规模遵循幂律关系，但收益递减明显
- Chinchilla 修订：参数量和训练数据应同比缩放
- 涌现能力表明规模会带来质的飞跃，而非仅仅是量的提升
- 实践中应结合 RAG、工具调用等策略，而非单纯追求更大模型

两者的结合构成了现代 AI Agent 的技术基石——大模型是"大脑"，Scaling Laws 告诉我们怎么做更强的大脑，而工具调用让大脑长出了"双手"。
