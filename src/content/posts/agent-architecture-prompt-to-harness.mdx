## 一、问题的起点：当"聊天"不够用了

2023 年，我们惊叹于 ChatGPT 能写诗、能翻译、能回答刁钻的常识问题。

2024 年，我们开始不满足——能不能帮我订机票？能不能帮我 debug 一个跨文件的 bug？能不能帮我管理一个为期三个月的项目？

从"聊天"到"干活"，需求变了。而需求变了，架构就必须跟着变。

在之前的文章[《大模型如何学会使用工具》](/blog/llm-tool-calling-scaling-laws)中，我们讨论过 Function Calling 的基础机制——模型如何声明工具、如何决策调用时机、如何把执行结果整合进回复中。那是 Agent 的"Hello World"：**一个工具、一步调用、一个结果**。

但郝建业老师（天津大学教授）在博见社的报告，实质上在问一个更上层的问题：**当工具多了、任务长了、环境复杂了，光靠 Function Calling 够吗？**

答案是：远远不够。而你需要的，是整个架构思维的根本性转变。

郝建业老师的报告《基于大语言模型的智能体》从宏观层面对 Agent 架构做了全景式梳理；张航帆老师（上海 AI Lab 青年研究员）的报告《智能体 Harness 的设计与演进》则从工程实践出发，展示了 Harness 生态的现状和一个极具创新性的"自我演进"框架。两场报告恰好构成了一条从"为什么"到"怎么做"的完整叙事弧线。

## 二、三大阶段：Prompt → Context → Harness

郝建业老师用一张图概括了 LLM-based Agent 架构的演进路线——这是全场最让我印象深刻的框架图之一：

![Agent 架构三大阶段演进](/images/blog/report-agent-arch-1.jpg)

他把 Agent 架构的演进分为三个清晰的阶段，每个阶段对应不同的技术范式和思维模型。理解这三个阶段，就理解了 Agent 领域过去五年发生的一切。

### 阶段一：Prompt Engineering（提示词工程）

这是最原始的形态。通过精心设计 prompt 中的角色定义、行为约束、Few-shot 示例和输出格式，让模型按预期方式行动。

**核心思维**：关注"怎么描述任务"。

这就像你给一个实习生写工作说明书——你花了大量精力把需求写清楚，但实习生做完第一步之后，你要重新告诉他第二步该干什么。Prompt Engineering 的**根本局限**就在这里：它没有状态管理能力。每一轮对话都是"失忆"的，模型不记得上一轮做了什么、做到了哪一步、中间遇到了什么问题。

### 阶段二：Context Engineering（上下文工程）

这一阶段的觉醒是：**光靠"描述"不够，要管理"模型看到什么"**。

Context Engineering 的核心是围绕上下文窗口做文章——把短期记忆（本轮对话）、长期记忆（历史经验）、工具返回结果（执行反馈）进行选择、组织、压缩，然后组装成一个高质量的信息包注入模型。

这一阶段的代表技术包括 RAG（检索增强生成）、ReAct（推理-行动循环）、记忆摘要与压缩等。相比 Prompt Engineering，它的进步在于**开始有了"状态"的概念**——模型不再完全失忆，可以通过外挂记忆和检索来维持一个任务上下文。

**但局限同样明显**：Context Engineering 只优化了"喂给模型什么信息"，它并不直接提供**真实的执行环境、工具权限、任务调度和失败恢复机制**。换句话说，你还是让一个更聪明的"实习生"去干活，但没有给他一个真正的"工位"。

### 阶段三：Harness Engineering（驾驭层工程）

这是当前 Agent 架构演进的前沿。郝建业老师给出的定义非常精准：

> Harness Engineering 围绕**运行闭环**，将信息组织成 Agent 可持续执行的系统。

它的关注点不再是"怎么说"或"让模型看什么"，而是：**怎么让 Agent 在真实环境中持续、可靠、可控地行动**。

这三者的对比可以用一句话概括：

- Prompt 回答 **"怎么描述"**
- Context 回答 **"让模型看到什么"**
- Harness 回答 **"怎么让 Agent 在真实世界中持续可靠地跑起来"**

## 三、Hermes：一个安全可控的持续成长型 Agent 框架

讲完宏观架构，郝建业老师引入了一个具体的框架案例——Hermes：

![Hermes 安全可控持续成长型 Agent 框架](/images/blog/report-agent-arch-2.jpg)

Hermes 的核心设计理念是 **Learning Runtime-first**——它不是简单地让 Agent"能跑"，而是强调 **"跑完之后能学到什么"**。

整个框架的工作流分为两个关键环节：

**执行前（A. 上下文组装）**：每次执行新任务之前，Hermes 会从多个来源——长期记忆、历史会话、技能库、项目约束——提取相关信息，自动组装成最适合当前任务的上下文。这比简单地把所有历史对话一股脑塞进 prompt 要高效得多。

**执行后（B. 经验沉淀）**：任务执行完不是终点。结果会被检验，成功的经验会沉淀为可复用的 **Skills（技能）**，失败的教训也会写入长期记忆。这样，一次性的任务执行被转化成了**可累积、可复用的能力**。

与开源的 OpenClaw 相比，Hermes 更强调**安全边界治理**：权限管控、访问控制、供应链边界都在框架层面有完备设计。局限在于 Skills 的质量目前还不太稳定，依赖长期使用才能打磨出高质量技能，且公开的对比评估数据较少。

**核心逻辑**：Hermes 在尝试回答一个关键问题——**Agent 不仅要会用工具，还要能从每次使用中长进。** 这正是 Harness Engineering 区别于前两个阶段的核心特征。

## 四、Coding Agent：模型强 ≠ 工程强

讲完框架，郝建业老师用 Coding Agent（代码智能体）作为具体的垂直场景，揭示了 Agent 能力的真正来源：

![Coding Agent 的能力提升——GLM-5.2 与状态机闭环](/images/blog/report-agent-arch-3.jpg)

这张图用一个清晰的对比回应了一个普遍的误解：**优秀的 Coding Agent 能力不只来自更强的模型，更来自更强大的工程闭环。**

左侧展示了 GLM-5.2 代码能力的三层来源——模型架构（长上下文 + 思维链推理）、训练数据（代码库样本 + 长任务场景 + 真实工作流轨迹）、训练算法（GRPO→PPO 的 RL 演进 + Online Anti-Hack 实时对抗 + 全链路训练）。

右侧则展示了更关键的**状态机闭环架构（State-Machine Loop Engineering）**。一个完整的代码执行周期包括：

```
Issue 初始化 → 环境准备 → 生成代码 → 执行代码 → 测试检验 → 失败再调试 → 经验沉淀
```

这是一个不断自我纠错的闭环。代码生成错了？测试没过？没关系，失败信息会被重新注入上下文，Agent 基于反馈再次尝试。这恰恰是 Prompt Engineering 做不到的事——它只能"说"，不能"调试"。

> **核心启示**：很多人以为 Agent 能力提升主要靠更好的基座模型。但从这张图来看，**Loop Engineering（闭环工程）的重要性至少和模型本身相当**。给一个强模型配上糟糕的闭环，就像一个天才工程师被塞在没有任何工具的空房间里——他再聪明也使不上劲。

## 五、记忆管理的两条路径：显式检索 vs 参数化记忆

记忆是 Agent 架构中最核心的组件之一，也是当前技术分歧最大的地方。郝建业老师用一张图展示了**两条截然不同的技术路线**：

![记忆管理的两条路径——显式检索 vs 参数化记忆](/images/blog/report-agent-arch-5.jpg)

### 路径一：显式检索（Hierarchical Memories）

这是目前的主流方案——把知识存在外部向量数据库里，需要时通过语义检索拉回来，注入上下文窗口。在之前的文章[《嵌入向量与语义搜索》](/blog/embedding-vector-semantic-search)中我们详细讨论过向量检索的原理。这套方案成熟、可控、可解释——你知道 Agent 在查什么、查到了什么。

**但它的根本问题在于"不可学习"**：检索策略是写死的规则，不会随着使用而优化。查多查少、查什么粒度、什么时候该检索什么时候不该检索——这些都是工程师拍脑袋定的，很难针对每个具体任务动态调整。而且外部检索天然存在延迟和带宽限制。

### 路径二：参数化记忆（MLP Memory）

这是一条更激进、也更前沿的路线——**把检索能力内化进模型参数本身**。

核心思路是：构建一个 KNN 数据库作为记忆库，但不像传统 RAG 那样"检索 → 拼进 prompt"，而是通过 **KL + CE 联合目标函数**预训练一个 MLP 记忆模块。这个模块学会了直接从模型内部"计算"出需要检索什么记忆，把显式的"查库"行为变成了模型内部的隐式计算。

**好处很明显**：更快（没有外部 IO）、可学习（记忆调用策略会随着训练优化）、不依赖外部知识库的规模。**代价**是训练的复杂度和记忆更新的灵活性——参数化记忆要加入新知识就得重新训练，不像向量数据库那样可以随时增删改。

> 我的判断：短期来看，两种路线会共存——显式检索处理"随时变化的知识"（如实时数据、个性化偏好），参数化记忆处理"稳定但需要快速访问的核心知识"（如通用常识、编程规范）。长期来看，参数化记忆如果能解决增量更新问题，可能会成为主流。

## 六、实战检验：MemoraX 的降维打击

讲了这么多理论，效果到底怎么样？郝建业老师用两个 Django 项目的真实 Bug 修复案例，给出了一个极具说服力的对比：

![MemoraX vs 原生 Claude Code——Django Bug 修复对比](/images/blog/report-agent-arch-6.jpg)

**场景一：Django 索引重命名**

原生 **Claude Code** 在处理这个任务时，由于无法排除历史中的无关信息，在长上下文干扰下反复重复重命名操作，导致测试用例持续失败。最终**消耗了 59.47M Token 仍然失败**。

而 **Claude Code + MemoraX**（具备记忆管理机制的增强版）能够过滤无关历史上下文，精准定位问题所在，仅用 **0.41M Token** 就完成了修复并通过所有测试。

**场景二：Django 字段检查**

更夸张。原生 Agent 会检索到无关历史记录，在庞大的上下文中忽略了关键逻辑；带 MemoraX 的 Agent 能快速定位已有字段定义，保持最新的约束和规则。Token 消耗从 **95.45M** 骤降至 **0.57M**——仅为原来的 **1/168**。

**为什么会差这么多？**

传统的规则式记忆只是简单"记录历史"，在长上下文中关键约束和规则容易被无关信息冲淡——就像你在一个喧闹的房间里试图回忆昨天听到的一句话。而 MemoraX 通过**记忆模型的训练和优化**，学会了**写入什么、筛选什么、何时调用**。这套 Loop Engineering 把记忆管理从"规则工程"升级成了**"可学习系统"**。

> **95M Token vs 0.57M Token，失败了 vs 成功了。** 这种量级的差距，不能用"模型更强了"来解释——是**记忆管理的范式升级**带来的结构性效率提升。

## 七、Harness 生态：一场正在爆发的运动

从郝建业老师的报告走出来，张航帆老师的报告恰好接棒——如果 Harness Engineering 是方向，那现在的 Harness 生态到底是什么样的？

![现有 Agent Harness 生态全景](/images/blog/report-harness-1.jpg)

张航帆老师给出了三个层次分明的生态图谱：

- 🟡 **编码 Harness**：Claude Code、Codex 等，专注开发场景，把 Agent 接入真实的代码仓库和开发环境。
- 🔵 **通用 Harness**：OpenClaw、Work Buddy 等，让 Agent 承担更广泛的任务，从文件管理到浏览器操作。
- 🟣 **Harness 构建框架**：DeepAgents、DeerFlow 等，提供深度定制专属 Agent 的基础设施，方便开发者快速搭建自己的 Agent。

三个数字抓住了这个领域的热度：
- **720K+ Stars**：6 个代表性项目累计的 GitHub 星数，说明开发者对这类工具的极高关注。
- **3.3 天**：平均每个仓库发布新版本的间隔，反映出迭代速度之快——几乎每天都在变。
- **29%**：GitHub 上已有 **29%** 的项目有 Agent 参与开发和维护，AI 智能体已深度融入开源生态。

**这个生态处于什么状态？** 我的感受是——**"形态多样、层次分明、快速演进"**。各路人马都在探索如何让 AI 更好地"接入"真实世界。但同时也意味着，目前还没有形成统一的最佳实践——每个人都在摸着石头过河。

## 八、Self-Harness：让 Agent 学会"自我调试"

如果说图 1 是"现状扫描"，那张航帆老师报告的真正亮点在图 2——一个名为 **Self-Harness** 的自我演进框架：

![Self-Harness 自我演进闭环框架](/images/blog/report-harness-2.jpg)

**这个框架最令人兴奋的地方在于：它不修改大模型本身的权重。** 它通过一个纯工程化的方式，让 Agent 像程序员 debug 自己的代码一样，不断优化自己的运行系统。

整个过程分为三个闭环阶段：

### 阶段 1：弱点挖掘（Weakness Mining）

让当前的 Harness（$h_t$）去执行一批任务，收集所有失败的执行轨迹。然后把失败原因聚类成特定的**"失败模式"**——比如"缺失输出验证"、"工具调用参数错误"、"路径探索不足"等等。

这一步的关键是**结构化地理解失败**——不是笼统地说"Agent 做得不好"，而是精准地识别出"在哪种情况下、因为什么原因、失败在了哪个环节"。

### 阶段 2：Harness 方案提议（Harness Proposal）

将聚类后的失败模式作为输入，使用一个**固定的基础模型（Fixed Model M）**作为裁判和提议者。

**这一环节是整个框架最大的创新点**：模型不更新自己的权重，而是去**修改 Harness 的配置**——调整 prompt 模板、变更工具集的参数策略、修改记忆存储和检索规则、增加或删减执行步骤。比如它可能提议："在输出最终答案前，增加一步自我验证的 Prompt"；或者"当工具调用返回错误码时，不要直接放弃，先尝试更换参数重试一次"。

### 阶段 3：方案验证（Proposal Validation）

对提议的修改方案进行**回归测试**。如果测试通过，则接受修改，生成升级版的 Harness（$h_{t+1}$），进入下一轮迭代。如果全部失败，则拒绝修改，保持原样。

---

把三个阶段串起来看，Self-Harness 做的是这样一件事：

> Agent 不断地"干活 → 犯错 → 分析错误模式 → 自动修改自己的运行配置 → 再干活 → 验证是否改进"。

**它不训练模型，它"训练"的是模型外面的那层驾驭层。**

这为 Agent 的可靠性问题提供了一条非常有吸引力的路径：与其花几百万美元重新训练一个"更不容易犯错"的大模型，不如在工程层面构建一个**自我诊断、自我修复、持续优化的运行时框架**。

## 九、总结：从"会聊天"到"会干活"，中间隔着一整套工程体系

把郝建业老师和张航帆老师的两场报告放在一起看，一条清晰的演进路径浮现出来：

1. **Prompt Engineering** 让模型能按照指令行动——但它是"一次性"的，没有状态，没有记忆。
2. **Context Engineering** 给模型配上了记忆和检索——但它仍然只是在"优化输入"，没有真正的执行环境。
3. **Harness Engineering** 终于构建起了完整的运行闭环——工具接入、状态管理、失败恢复、经验沉淀，全部纳入一个可控的系统。

而在 Harness Engineering 这个阶段，我们看到了两条互相支撑的路线：

- **Hermes** 式的持续成长框架——让 Agent 从每次执行中学到东西，把一次性任务转化为可累积的能力。
- **Self-Harness** 式的自我演进机制——不重训模型，而是让 Agent 自动发现弱点、自动修改配置、自动验证改进。

再加上**参数化记忆**对传统向量检索的挑战，和 MemoraX 案例展示的 **168 倍 Token 节省**——这些都在指向同一个方向：

> **Agent 的未来不只取决于模型有多强，更取决于模型外面的那层"驾驭层"有多聪明。**

"会聊天"只需要一个好的基座模型。"会干活"需要一整套工程体系。
