## 项目概览

五子棋是我博客的附属项目，经历了从纯前端人机对弈，到 WebSocket 在线联机，再到 Nginx 生产部署的完整迭代。整个项目零依赖运行——前端是单个 HTML 文件（Canvas 渲染），后端仅用 `ws` 库做 WebSocket 通信。

访问地址：[/gomoku](/gomoku)

## AI 引擎：Minimax + Alpha-Beta 剪枝

人机对战的 AI 分三个难度等级，核心是 Minimax 搜索：

```
困难：Minimax 深度 6 + Alpha-Beta 剪枝 + 杀手走法启发式
中等：Minimax 深度 4
简单：纯启发式评估（无搜索）
```

### Alpha-Beta 剪枝原理

Minimax 需要遍历所有可能的棋盘状态，复杂度 O(b^d)。Alpha-Beta 剪枝通过维护 α（己方当前最优下界）和 β（对手当前最优上界），剪掉不可能改变决策的分支，在不损失精度的前提下将实际搜索节点数降低到 O(b^(d/2))。

```
α-β 剪枝的核心：
- α：最大化节点，己方已保证的最低分
- β：最小化节点，对手已保证的最高分
- 当 α ≥ β 时发生剪枝，不再搜索该分支
```

### 杀手走法启发式

每次搜索记录触发剪枝的走法（"杀手走法"），下一次搜索优先尝试。经验表明，上次剪枝成功的位置更可能在本次也触发剪枝，这进一步提升了搜索效率。

### 局面评估

启发式函数对每个空格打分，考虑以下因素：
- **连子数**：同色连续棋子越长，分数越高
- **两端开放性**：两端均开放（活棋）的连子价值远高于一端被封堵（眠棋）
- **攻守平衡**：同时评估己方和对手的得分，加权求和

评分表大致如下（以五连为最大）：

| 形状 | 活四 | 眠四 | 活三 | 眠三 | 活二 |
|------|------|------|------|------|------|
| 分值 | 100000 | 10000 | 1000 | 100 | 10 |

## 在线联机架构

在线模式的整体架构：

```
iframe (public/gomoku/index.html) ← postMessage → React 页面
    ↕ WebSocket
ws-server.ts (Node.js, 端口 3001)
    ↕ 共享内存 (room-store.ts)
API Route (/api/gomoku/rooms)
```

### 房间管理

设计了两个固定房间（Room A / Room B），无论有没有人在玩都一直存在。这样做的好处是简单可靠，不需要动态创建/销毁房间。

状态流转：

```
empty → (Guest 1 进入) → waiting → (Guest 2 进入) → playing → finished
  ↑                                                              |
  └────────────── 30s 超时解散 / 玩家离开 ←──────────────────────┘
```

- **Guest 1**：先进入房间的玩家，执黑先行。进入后启动 30 秒倒计时，无人加入则自动解散
- **Guest 2**：后进入的玩家，执白。进入后倒计时取消，对局开始
- **再来一局**：双方都投票后，棋盘重置，不改变角色分配
- **悔棋**：任意一方发起即生效，恢复上一步的状态

### WebSocket 消息协议

客户端与服务端通过 JSON 消息通信，核心消息类型：

| 消息 | 方向 | 说明 |
|------|------|------|
| `join-room` | → | 玩家加入房间 |
| `place-piece` | → | 玩家落子（服务器校验） |
| `undo-request` | → | 请求悔棋 |
| `request-rematch` | → | 投票再来一局 |
| `leave-room` | → | 离开房间 |
| `room-state` | ← | 房间完整状态快照 |
| `opponent-move` | ← | 对手落子通知 |
| `game-over` | ← | 对局结束 + 获胜者 |
| `undo-applied` | ← | 悔棋已生效 |
| `rematch-accepted` | ← | 双方同意再来一局 |
| `countdown` | ← | 倒计时（等待对手时每秒推送） |

### 服务器端校验

所有落子由服务端做最终裁判：

1. 校验回合顺序（防止客户端作弊连下）
2. 校验落子位置合法性（不越界、不覆盖）
3. 四方向扫描判定胜负（横、竖、两条对角线）
4. 满盘判定平局

这种方式确保了对局的公平性——客户端只负责 UI 展示，服务端掌握最终状态。

## Nginx 反向代理

生产环境中，WebSocket 通过 Nginx 代理到后端：

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
```

关键点：必须设置 `Upgrade` 和 `Connection` 头，否则 WebSocket 握手失败，客户端会连接超时。`proxy_read_timeout` 设置为较长时间防止对局中途断开。

## Canvas 棋盘渲染

棋盘和棋子全部用 Canvas 绘制，特点：

- **木质纹理**：通过多层渐变叠加模拟木板质感
- **棋子 3D 光泽**：径向渐变 + 高光偏移，黑白棋子各有立体感
- **悬停预览**：鼠标移动时半透明预览落子位置
- **获胜连线高亮**：判定胜负后，连成五子的位置用脉冲动画高亮

## 排行榜

游戏结束后，人机模式可将成绩提交到排行榜：

- `POST /api/gomoku/score` — 提交成绩
- `GET /api/gomoku/score` — 获取排行榜
- 数据持久化到 `src/data/gomoku-scores.json`

## 技术总结

| 层次 | 技术选择 | 理由 |
|------|---------|------|
| 游戏 UI | Canvas 2D | 零依赖，全自定义渲染 |
| AI 搜索 | Minimax + α-β | 经典博弈树算法，深度 6 可达中高级水平 |
| 实时通信 | WebSocket (ws) | 双向低延迟，适合实时对弈 |
| 房间状态 | 共享内存 + JSON 文件 | 简单可靠，无需 Redis |
| 反向代理 | Nginx | 统一入口，处理 WS 升级 |
| 成绩存储 | JSON 文件 | 数据量小，无需数据库 |
